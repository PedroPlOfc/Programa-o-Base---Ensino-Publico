## 1. O que é Git e por que ele existe?

Antes de aprender comandos, entenda **o problema que o Git resolve**.

### O Problema (sem Git)

Imagine que você está desenvolvendo um site. Em algum momento você faz isso:

```
projeto_v1/
projeto_v2/
projeto_v2_final/
projeto_v2_final_agora_vai/
projeto_ESSE_AQUI/
```

Isso é caótico, ocupa espaço e você nunca sabe qual é o real. Agora imagine **2 pessoas** editando os mesmos arquivos ao mesmo tempo — viraria um desastre de arquivos sobrescritos.

### A Solução: Controle de Versão

O **Git** é um sistema de controle de versão distribuído criado por **Linus Torvalds** (o mesmo criador do Linux) em 2005. Ele resolve exatamente esses problemas:

- ✅ Guarda **todo o histórico** de mudanças do projeto
- ✅ Permite **trabalhar em equipe** sem conflito caótico
- ✅ Permite **voltar no tempo** para qualquer versão anterior
- ✅ Cada desenvolvedor tem uma **cópia completa** do repositório
- ✅ Funciona **offline** — você não precisa de internet para commitar

### 🎮 Analogia: O Sistema de Save State

Pense num RPG difícil. Você salva o jogo antes de cada batalha perigosa. Se perder, carrega o save e tenta de novo — sem perder todo o progresso.

O Git funciona **exatamente assim** com seu código:

| Conceito do Jogo        | Conceito Git                  | O que significa                               |
|-------------------------|-------------------------------|-----------------------------------------------|
| Salvar o jogo           | `git commit`                  | Cria um checkpoint permanente do código       |
| Carregar save           | `git checkout` / `git restore`| Volta para um estado anterior                 |
| Múltiplos slots de save | `git branch`                  | Linhas paralelas de desenvolvimento           |
| Jogar na nuvem          | `git push`                    | Envia seu progresso para o GitHub             |
| Baixar save da nuvem    | `git pull`                    | Sincroniza o repositório remoto para o local  |
| Ver histórico de saves  | `git log`                     | Lista todos os commits feitos                 |

## 2. Git vs GitHub — Diferença Real

Muitos iniciantes confundem os dois. São coisas **completamente diferentes**:

```
┌─────────────────────────────────────────────────────┐
│  GIT                                                │
│  • Software instalado na SUA máquina               │
│  • Funciona 100% offline                           │
│  • Gerencia versões localmente                     │
│  • Linha de comando (terminal)                     │
└─────────────────────────────────────────────────────┘
                        ↕ sincroniza via push/pull
┌─────────────────────────────────────────────────────┐
│  GITHUB                                             │
│  • Plataforma web (github.com)                     │
│  • Hospeda repositórios Git na nuvem               │
│  • Colaboração entre devs (Pull Requests, Issues)  │
│  • CI/CD, Actions, Pages, etc.                     │
└─────────────────────────────────────────────────────┘
```

> **Resumo prático:** Git é a ferramenta. GitHub é a plataforma social/profissional onde você hospeda e compartilha seu código. Existem alternativas ao GitHub como **GitLab** e **Bitbucket**, mas funcionam com o mesmo Git.

## 3. Como o Git Funciona por Dentro

Entender as **três áreas do Git** é fundamental para não se perder:

```
┌──────────────────┐    git add    ┌──────────────────┐    git commit   ┌──────────────────┐
│  WORKING TREE    │ ────────────► │  STAGING AREA    │ ──────────────► │   REPOSITORY     │
│  (Diretório)     │               │  (Index / Stage) │                 │   (Histórico)    │
│                  │               │                  │                 │                  │
│  Seus arquivos   │               │  Arquivos        │                 │  Commits         │
│  que você edita  │               │  prontos para    │                 │  permanentes     │
│  no VS Code      │               │  o próximo commit│                 │  (.git/)         │
└──────────────────┘               └──────────────────┘                 └──────────────────┘
       ▲                                                                        │
       └────────────────────────────── git restore ◄──────────────────────────┘
```

### Working Tree (Área de Trabalho)
É simplesmente a **pasta do seu projeto**. Quando você abre um arquivo e edita, está trabalhando aqui. O Git "vê" as mudanças, mas ainda não as registrou.

### Staging Area (Palco / Index)
É uma área intermediária — um **rascunho preparatório** para o próximo commit. Você escolhe exatamente quais mudanças vão entrar no próximo checkpoint. Isso permite commits cirúrgicos e organizados.

### Repository (Repositório / .git)
É onde o histórico de verdade vive — dentro da pasta oculta `.git` no seu projeto. Cada `git commit` grava um snapshot permanente aqui.

## 4. Instalação e Configuração Inicial

### Instalando o Git

- **Windows:** Baixe em [git-scm.com](https://git-scm.com) e instale normalmente.
- **macOS:** `brew install git` ou `xcode-select --install`
- **Linux (Debian/Ubuntu):** `sudo apt install git`

Verifique a instalação:
```bash
git --version
# git version 2.43.0
```

### Configuração Obrigatória (faça uma vez)

Essas configurações identificam **quem você é** em cada commit. Use o mesmo e-mail do GitHub.

```bash
# Seu nome completo (aparece no histórico de commits)
git config --global user.name "Seu Nome Completo"

# Seu e-mail (DEVE ser o mesmo do GitHub)
git config --global user.email "seu@email.com"

# Define o editor padrão para mensagens de commit
git config --global core.editor "code --wait"   # VS Code
# git config --global core.editor "vim"         # Vim (alternativa)

# Define 'main' como nome padrão da branch principal (padrão moderno)
git config --global init.defaultBranch main

# Melhora exibição de nomes de arquivos com acentos (importante no Windows)
git config --global core.quotepath false
```

### Verificando a Configuração

```bash
# Lista todas as configurações globais
git config --global --list

# Verifica um item específico
git config user.name
git config user.email
```

### Onde ficam essas configs?

As configurações globais ficam num arquivo chamado `.gitconfig` na sua pasta de usuário:
- **Windows:** `C:\Users\SeuNome\.gitconfig`
- **macOS/Linux:** `~/.gitconfig`

```bash
# Abre o arquivo de config diretamente
git config --global --edit
```

## 5. Seus Primeiros Comandos

### `git init` — Criar um repositório do zero

```bash
# Dentro da pasta do seu projeto, execute:
git init

# Saída esperada:
# Initialized empty Git repository in C:/projeto/.git/
```

Isso cria a pasta oculta `.git` dentro do projeto. **Nunca apague essa pasta** — ela contém todo o histórico.

```bash
# Verificando que foi criada:
ls -a        # macOS/Linux
dir /a       # Windows
# Você verá: .git
```

### `git status` — Seu "radar" principal

Este é o comando que você **mais vai usar**. Ele mostra o estado atual de todos os arquivos:

```bash
git status
```

**Interpretando a saída:**

```
On branch main                          ← branch atual

Untracked files:                        ← arquivos novos, Git não conhece ainda
  (use "git add <file>..." to include in what will be committed)
        index.html
        style.css

Changes not staged for commit:          ← arquivos conhecidos mas modificados
  (use "git add <file>..." to update what will be committed)
        README.md

Changes to be committed:                ← no stage, prontos para commit
  (use "git restore --staged <file>..." to unstage)
        app.js
```

| Status                      | Cor (terminal) | Significado                              |
|-----------------------------|----------------|------------------------------------------|
| `Untracked`                 | 🔴 Vermelho    | Git nunca viu esse arquivo               |
| `Modified` (not staged)     | 🟡 Amarelo     | Arquivo modificado mas fora do stage     |
| `Modified` (staged)         | 🟢 Verde       | No stage, vai entrar no próximo commit   |
| `nothing to commit`         | —              | Tudo limpo, sem mudanças pendentes       |

### `git add` — Adicionando ao Stage

```bash
# Adiciona UM arquivo específico
git add index.html

# Adiciona VÁRIOS arquivos de uma vez
git add index.html style.css app.js

# Adiciona todos os arquivos de uma pasta
git add src/

# Adiciona TUDO (arquivos novos + modificados)
git add .

# Adiciona interativamente (escolhe trecho por trecho)
git add -p nome-do-arquivo.js
```

> 💡 **Dica Sênior:** Prefira `git add -p` quando quiser fazer commits cirúrgicos, adicionando só partes específicas de um arquivo.

### `git commit` — Criando o Checkpoint

```bash
# Commit com mensagem direta (mais usado)
git commit -m "feat: adiciona página inicial com menu de navegação"

# Commit abrindo o editor (para mensagens mais longas)
git commit

# Atalho: add + commit em um comando (só para arquivos já rastreados)
git commit -am "fix: corrige bug no formulário de contato"
```

**Anatomia de um bom commit:**
```
feat: adiciona autenticação com JWT

- Implementa middleware de validação de token
- Adiciona rota /login e /logout
- Configura expiração de 24h para os tokens

Closes #42
```

- **Linha 1:** Tipo + descrição curta (máx. 72 caracteres)
- **Linha 2:** Em branco (separador)
- **Linhas 3+:** Descrição detalhada, bullet points, referências

## 6. O Fluxo de Trabalho Diário Completo

Este é o ciclo que você vai repetir **todo dia** como desenvolvedor:

```
Editar código → status → add → commit → push → (repete)
```

### Passo a Passo Detalhado

**Passo 1 — Verifique o que mudou antes de qualquer coisa:**
```bash
git status
git diff          # Mostra as diferenças linha por linha
git diff --staged # Mostra diferenças dos arquivos já no stage
```

**Passo 2 — Adicione os arquivos relevantes:**
```bash
git add .
# ou seletivamente:
git add src/components/Header.js
```

**Passo 3 — Confirme o que vai entrar no commit:**
```bash
git status        # Veja o que está no stage (verde)
git diff --staged # Revise as mudanças linha por linha
```

**Passo 4 — Faça o commit:**
```bash
git commit -m "feat: adiciona componente Header responsivo"
```

**Passo 5 — Envie para o GitHub:**
```bash
git push
```

**Passo 6 — Antes de começar um novo trabalho, sempre atualize:**
```bash
git pull          # Baixa as mudanças dos outros devs
```

### Exemplo Realista de um Dia de Trabalho

```bash
# Começo do dia — atualiza
git pull origin main

# ... você trabalha, edita arquivos ...

# Verifica o que mudou
git status

# Adiciona e commita por funcionalidade (não jogue tudo junto!)
git add src/features/auth/
git commit -m "feat(auth): implementa tela de login"

git add src/features/dashboard/
git commit -m "feat(dashboard): adiciona gráfico de vendas"

# Sobe tudo para o GitHub
git push
```

> ⚠️ **Erro comum:** Commitar tudo de uma vez com `git add .` e uma mensagem vaga como "alterações". Isso dificulta revisões e o rastreamento de bugs no futuro.

## 7. Conectando ao GitHub

### Criando seu Primeiro Repositório Remoto

1. Acesse [github.com](https://github.com) e faça login
2. Clique em **"New repository"** (botão verde)
3. Dê um nome, escolha público ou privado, **NÃO inicialize com README** (já temos código local)
4. Clique em **"Create repository"**
5. O GitHub mostrará os comandos — use o bloco **"…or push an existing repository"**

### Comandos de Conexão

```bash
# Adiciona o repositório remoto (apelido padrão: origin)
git remote add origin https://github.com/seu-usuario/seu-repo.git

# Verifica os remotos configurados
git remote -v
# origin  https://github.com/seu-usuario/seu-repo.git (fetch)
# origin  https://github.com/seu-usuario/seu-repo.git (push)

# Primeiro push: -u define o upstream (só precisa uma vez)
git push -u origin main

# Nas próximas vezes:
git push
```

### Autenticação com Token (GitHub exige desde 2021)

O GitHub não aceita mais senha — usa **Personal Access Token (PAT)**:

1. GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic)
2. Generate new token → marque `repo` e `workflow`
3. **Copie o token** — ele aparece só uma vez
4. Quando o terminal pedir senha, cole o token no lugar

```bash
# Salva credenciais para não precisar digitar sempre
git config --global credential.helper store       # Linux/Mac
git config --global credential.helper wincred     # Windows
```

## 8. O Arquivo .gitignore

O `.gitignore` instrui o Git a **ignorar arquivos** que não devem ir para o repositório.

### Por que ignorar arquivos?

- `node_modules/` — milhares de arquivos que podem ser reinstalados com `npm install`
- `.env` — senhas, chaves de API, dados sensíveis
- `*.log` — logs de sistema
- `.DS_Store` — metadados do macOS
- `dist/` ou `build/` — arquivos gerados automaticamente

### Criando o .gitignore

```bash
# Crie na raiz do projeto
touch .gitignore   # macOS/Linux
# No Windows, crie pelo VS Code (Ctrl+N → salvar como .gitignore)
```

**Exemplo de .gitignore para um projeto Node.js:**

```gitignore
# Dependências (sempre ignorar)
node_modules/
.pnp
.pnp.js

# Variáveis de ambiente (NUNCA commitar)
.env
.env.local
.env.development.local
.env.test.local
.env.production.local

# Build
dist/
build/
.next/
out/

# Logs
*.log
npm-debug.log*

# Sistema operacional
.DS_Store         # macOS
Thumbs.db         # Windows

# Editor
.vscode/settings.json
.idea/
*.swp

# Cache
.eslintcache
.cache/
```

### Sintaxe do .gitignore

```gitignore
# Comentário
segredo.txt          # ignora arquivo específico
*.log                # ignora todos os .log
logs/                # ignora pasta inteira
!logs/important.log  # exceção: NÃO ignora este arquivo específico
**/temp              # ignora pasta 'temp' em qualquer nível
doc/**/*.txt         # ignora .txt dentro de doc/ (qualquer subpasta)
```

> 💡 **Dica:** Use o site [gitignore.io](https://www.toptal.com/developers/gitignore) para gerar `.gitignore` customizado para sua linguagem/framework.
